# Camera sensors in the vendor A9 firmware

The vendor application for the A9 camera (`com.naxclow.Camera_v0-1.1.20`, board string
`NAXC_2M_48P_B_A9`) supports 11 DVP sensors. This document lists, for each one, the I2C
address, the probe, the init table and the other per-sensor settings the firmware applies.

Source image: the app partition dump `backups/app_2024-10-04_225830_A9_B_V1.9_230615_crc.bin`
(build date 2023-09-05). All addresses below are CPU addresses in that image: strip the CRC
bytes (`tools/uncrc`) and add `0x10000` to the file offset.

## How it was obtained

- The sensor list and the per-sensor functions come from the firmware's own descriptor table
  (see below).
- Each per-sensor function was run in isolation under Unicorn with the I2C read/write helpers
  replaced by loggers. For a probe, every value of every register it reads was tried until the
  probe reported success; that value is the expected ID.
- The V1.9 image never reaches the camera code when run in `bk7252-emulator`: video starts only
  on a request from the app or the cloud. The older `A9_B_V1.3_220516` image starts video at
  boot; its HI704 traffic in the emulator matches the HI704 table below (see Notes).

## Sensor descriptor

Each sensor is one 7-word descriptor in `.data`:

| offset | field                                              |
|--------|----------------------------------------------------|
| `+0`   | name (C string)                                    |
| `+4`   | `probe()`: returns 0 when the sensor answered      |
| `+8`   | `init()`: writes the init table                    |
| `+12`  | `mode(n)`: `n` is 0 or 1                           |
| `+16`  | always 0                                           |
| `+20`  | `frame_size(n)`: JPEG frame size limits, `n` 0..2  |
| `+24`  | `orientation(n)`: mirror/flip, `n` 0..4            |

A const array of 11 descriptor pointers at `0xB2A30` sets the probe order:

`gc0328`, `gc0308`, `sp0718`, `sp0a28`, `gc0312`, `gc0310`, `gc0309`, `gc0329`, `hi704`,
`ov7675`, `ov7690`.

Detection (`0x60148`) walks this list, calls `probe()` of each entry and calls `init()` of the
first one that returns 0. If none answers, it walks the list once more, then gives up. A
detection result variable starts at 2 ("pending") and becomes 0 or -1; the camera start code
polls it every 100 ms.

## I2C access

- All registers are 8-bit with 8-bit values.
- `write(addr, reg, value)` sends `reg value` in one transaction; `read(addr, reg, &value)`
  writes `reg`, then reads one byte.
- An init or mode table is a list of `{reg, value}` pairs written in order with no delays. An
  entry such as `FF FF` is written to the sensor like any other pair; the firmware has no marker
  values.
- The firmware uses the hardware I2C1 controller.

## Per-sensor functions

- `mode(n)`: a periodic task picks `n` from a board input and calls `mode(n)`; after start the
  camera code calls `mode(0)`. On several sensors `mode(1)` switches the picture to grey
  (`43`=`02` on GalaxyCore parts), so 1 is most likely night (IR) and 0 day.
- `frame_size(n)`: writes JPEG `target_byte_h` (`0x0080A008`, max bytes per frame) and
  `target_byte_l` (`0x0080A00C`, min bytes per frame) for the bit-rate control. The wrapper that
  calls it handles `n == 3` itself (max `0x4800`, min `0x3C00`) without calling the sensor.
- `orientation(n)`: writes one mirror/flip register; `n == 0` writes the same as `n == 1`.
- Three sensors write JPEG `CTRL0` = `0x10` before their init table: `clk_div` = 1, MCLK 16 MHz.
  The others leave MCLK as the camera code set it.

## Notes

- GC0310: the GC0310 table in the `beken_freertos_sdk` git history (commit `1af1d4f`) is this
  table with `F3`=`00` instead of `F3`=`FF` in entry 7, `46`=`03` instead of `46`=`07`, and an
  extra `F3`=`FF` at the end.
- HI704: in the V1.3 image the init sequence seen on the bus equals the V1.9 table below with
  one extra pair `11`=`90` after the first `03`=`00`. The project's
  `src/platform/devices/camera/sensors/hi704_init_table.h` differs from both in about 30
  registers.
- Not verified: the V1.9 camera path was not run end to end, so the delays between detection,
  init and `mode(0)` are not measured.
